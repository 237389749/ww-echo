## 0. 一页结论

**骨架是对的，呈现层还是"默认件堆叠"。** 信息架构（运行 / 穷举 / 配置 / 诊断）与游戏语义一致，
文案大多数时候具体、可操作；但视觉上仍是 qfluentwidgets 的 SettingCard 清单：每张卡一个图标 + 标题 +
一句说明 + 右侧控件，没有产品识别，也没有为"数据密集 + 长任务"做过排版。

先修 4 个可用性缺陷（都是可验证的 bug，不是审美问题）：

1. **所有数值输入框看不到数值**（qfluentwidgets 1.11.3 + PySide6 6.12.0；LineEdit 被压成 1px 宽）。
   影响套装权重、共效/暴击门槛、补正、条件补正 —— 所有要填数字的地方。
2. **套装配置页在最小窗口 940×620 下控件互相覆盖**（页面没有滚动容器，固定卡片 + 表格 stretch）。
3. **评估模式的状态卡显示的是强化模式的计数**：跑 12~20 分钟，一直显示「成功 0 / 失败 0 / 得分 -」，
   真正在涨的「评估数量」没显示。
4. **评估汇总把「不合格」和「不建议强化」合并成「不合格」**（`fail` 一个码两档文案；报告已经拆开）。
   同类问题还有报告「评估规则」卡片漏写了"低置信才下滑读明文"这一步。

再排 6 个高影响改进：

- 运行页首屏看不到日志（1120×760 时日志卡只露出标题与工具栏；最小窗口整块在折叠之下）——
  而评估刚改成 ~12 分钟。
- 组合穷举：7 张输入卡 + 环境卡 + 裸面板/补正表 + 结果卡，按钮和结果都在折叠之下；
  结果表行话多、数字左对齐、行高 2 行。
- 报告：一行 150px、1000px 只看得到 4 行；「词条明细」是公式墙；判定色对比度 2.2~3.7:1（低于 AA）。
- 导航默认纯图标（7 项无文字），首次使用只能靠试。
- 当前模式（图标优先 / 精确模式）只在启动日志里说一次，界面上没有持续指示。
- 空状态缺失（日志、目标窗口、截图/交互下拉）；说明文字在窄窗口被裁。

设计方向建议：保留 Fluent 骨架，建立一套"**调律台**"仪表语言 ——
冷灰画布、单一黄铜信号色、语义判定色阶、等宽数字右对齐；把唯一的记忆点放在运行状态条，
其余装饰（卡片阴影、圆角、大留白）全部收敛。

## 2. 现状盘点（设计 token）

代码里没有集中的 token 文件；颜色、字号、圆角散落在 `ui/*.py`、内联 HTML/CSS、QSS 三处。

| 维度 | 现状 | 问题 |
|---|---|---|
| 画布/表面（亮） | 画布 `#f0f4f9`，卡片 `#f7f9fc` | 亮度只差 ~3%，卡片靠 1px 边框和阴影区分 |
| 画布/表面（暗） | 画布 `#202020`，卡片 `#272727` | 层级同样偏弱；卡片看起来像"稍微亮一点的背景" |
| 强调色 | Fluent 蓝（开始按钮 `#0078d4` 一带） | 只用于主按钮，没有品牌识别 |
| 判定色（报告行） | Material 原色：`#4caf50 / #009688 / #2196f3 / #ff9800 / #f44336` | 白底对比度 2.16~3.68:1，全部低于 AA 4.5 |
| 判定色（报告摘要） | 深一档：`#2e7d32 / #00695c / #1565c0 / #e65100 / #c62828 / #b71c1c` | 与行内是**两套调色板**，同一判定两种颜色 |
| 字体 | `Microsoft YaHei UI` 系统字体；Title 28 / Subtitle 20 / Body 14 / Caption 12 | 没有字重/字距策略；数据不用等宽数字 |
| 圆角 | 4 / 6 / 8 混用（卡片 8、输入 5、表格 8、报告卡 8、标签 3） | 没有层级含义 |
| 阴影 | 报告卡片 `0 1px 4px rgba(0,0,0,.1)`；应用内 Fluent 自带 | 属于"SaaS 卡片套件"的默认做法 |
| 间距 | 页边距 24；卡片间距 16；SettingCard 固定高 70 | 窄窗口下固定高卡片会挤压/裁切内容 |
| 图标 | Fluent 线性图标；另有 `⚠ ✔ ✘ ·` 文本符号 | 符号字体回退不稳（表格里 `⚠` 在部分字体下变方块），且无 legend |
| 动效 | 无（InfoBar 淡入、进度条） | 长任务没有"正在做什么"的持续动效，只有日志 |

### P0 — 直接阻碍使用

#### U-01 所有 SpinBox 的数值不可见

- **现象**：套装配置的 13 个权重、低权重门槛、组合穷举的共效/暴击/补正/条件补正 —— 输入框只显示
  上下箭头，看不到数值；键盘输入也看不到。截图：`03_setconfig_892.png`、`logs/ui_audit/plan_spins_zoom.png`。
- **证据**：`DoubleSpinBox(120×33).lineEdit().geometry() == QRect(0, 1, 1, 31)`；
  真实 Windows 平台（200% DPI）同样复现。环境 `PySide6 6.12.0 + PySide6-Fluent-Widgets 1.11.3`。
  qfluentwidgets 的 `SpinBoxBase` 在 QAbstractSpinBox 上额外挂了一个 `QHBoxLayout` 放两个按钮，
  Qt 6.12 下样式计算出 1px 的编辑区。
- **影响**：所有数值类输入等于盲填；套装权重这种需要"看当前值再微调"的操作无法完成。
- **修复（已验证可行）**：在 `ui/widgets.py` 提供子类，`resizeEvent` 里手动摆 LineEdit：

  ```python
  class NumberSpin(DoubleSpinBox):
      RIGHT_RESERVED = 74          # 两个 31px 按钮 + 间距/边距
      def resizeEvent(self, e):
          super().resizeEvent(e)
          self.lineEdit().setGeometry(9, 1, max(20, self.width() - self.RIGHT_RESERVED), self.height() - 2)
  ```

  已验证 120/160/80 三种宽度下数值正常显示（`logs/ui_audit/spin_patched.png`）。
  备选：把 PySide6 钉回 6.8/6.9，或升级 qfluentwidgets（需先验证兼容性）。
- **回归**：加一条像素断言（spin 抓图最暗像素 < 120），避免只测 `text()` 测不出渲染问题。

> **✅ 已修（B1 / 补记 74）**：`ui/widgets._SpinLineEditFix` + `NumberDoubleSpinBox`/`NumberSpin`（别名导入，
> 13 处构造点未改）。与原稿的差异：①预留量**问布局要**（`hBoxLayout.sizeHint().width()`=71），写死 74 会让
> 文字钻到按钮底下 6px；②"编辑区 ≥20px"不够 —— 控件 < ~105px 时 `0.10` 会显示成 `0.1C`，已把 6 个过窄的
> 数值框加宽到 124，并把验收升级成"放得下文本 + 4px"。守卫：`tests/test_ui_guards.py` + 探针 C1。

#### U-02 套装配置页在最小窗口（940×620）下布局重叠

- **现象**：模板卡、导入/导出、权重表、首条判定互相覆盖；表格只露 1 行就被下方卡片压住。
  证据：`03_setconfig_892.png`（892×570 内容区，对应 940×620 窗口）。
- **根因**：`ui/set_config_tab.py:36` 是根 `QVBoxLayout`，`layout.addWidget(self.table, 1)`；
  没有滚动容器。窗口高度 < 内容最小高度时，Qt 把超出部分裁掉/覆盖。
- **修复**：整页套 `SingleDirectionScrollArea`（与设置页一致）；表格给 `setMinimumHeight(260)` 并让
  表格内部滚动，不要让 stretch 与固定卡片抢高度。
- 同类：调试工具页（日志区在 620 高时只剩 60px 且底部被裁）、开发者页同样没有滚动容器。

> **✅ 已修（B1 / 补记 74）**：两页都套页面级 `SingleDirectionScrollArea`（表格/日志卡 `setMinimumHeight(260)`）。
> 调试页**还多修一层**：`QStackedWidget` 按最高子页预留高度（截图页预览图 min 200 → OCR 页也被撑到 419），
> 加了 `_fit_stack()` 按当前页 sizeHint 定高 —— 892×570 下日志卡从"60px 且被裁"变成 379px / 17 行。

#### U-03 评估模式的状态卡显示强化模式的计数

- **现象**：评估跑 12~20 分钟，顶部一直是「成功: 0 失败: 0 得分: -」；真正在涨的 `评估数量` 不显示。
- **证据**：`ui/run_tab.py:474-477` 读 `成功声骸数量/失败声骸数量/声骸得分`；
  `src/task/EnhanceEchoTask.py:1652` 评估链只写 `info_set('评估数量', evaluated)`。
- **修复**：按任务类型分支 —— 评估显示「已记录 N · 失败 M · 用时」+ 每屏/总数；强化保持现状。
  同时把「得分」在评估模式下换成「平均完成度」或去掉（单只得分没有意义）。

> **✅ 已修（B1 / 补记 74）**：`ui/present.status_texts(task, is_eval)` 出文案 —— 评估 = 已记录 / 失败 / **结束原因**
> （第三格没用"用时"：耗时已有单独标签，而"为什么停"以前只写在日志里）；评估链补 `评估失败`
> （`_register_fail` 累加，只统计"点了没读到"、不含重复）与 `评估结束原因`（0级尾部/到底/受阻/用户停止/完成）。
> 「平均完成度」没放进状态卡（它要有报告数据，属于「上次评估结果」卡）。

#### U-04 评估汇总结论把「不合格」与「不建议强化」合并

- **现象**：「上次评估结果」卡显示「不合格 36」，而报告与筛选中是「不合格 21 + 不建议强化 15」。
- **证据**：`ui/run_tab.py:665-672` 用 `verdict` 码映射，表里 `fail → 不合格`；报告侧
  `ui/run_tab.py:902-905` 已按 `verdict_cn` 拆开。两处口径不一致。
- **修复**：汇总与报告共用一份"按 `verdict_cn` 归一化"的函数；`zero` 已不会入报告，从映射表删掉。

> **✅ 已修（B1 / 补记 74）**：`ui/present.count_verdicts` / `summary_text` —— 汇总卡、报告摘要、报告行内配色
> 共用同一份六档口径（`fail` 一个码里装两档，按码配色/计数都分不开）。守卫：探针 C4 + `test_ui_guards`。

### P1 — 明显影响效率/理解

#### U-05 运行页：长任务看不见日志，进度会随滚动消失

- 1120×760 时日志卡只露出标题与工具栏（约 70px）；940×620 时整块在折叠之下。
- 整页是一个 `SingleDirectionScrollArea`（`ui/run_tab.py:85-89`），日志卡虽然有 stretch，
  但在滚动容器里只能按 sizeHint 分配高度。
- **影响**：这是评估/强化的主监控面。用户要么滚下去看日志（丢掉进度），要么盯着看不到细节的状态卡。
- **建议**：运行页不要整页滚动。改成"固定状态条 + 下方两栏（左设置 360px 可滚，右日志填满剩余高度）"；
  或至少把状态条 sticky 在顶部、日志卡最小 340px。

#### U-06 导航默认收起为纯图标

- `ui/main_window.py:91` 只 `setExpandWidth(190)`，从未 `expand()`；启动看到的是 7 个无语义图标
  （房子/网格/齿轮/书/扳手/`{}`/ⓘ）。
- **建议**：默认展开；或首次启动展开一次并记住用户选择。中文标签比图标重要 —— 这些页名不是通用隐喻。

#### U-07 当前模式（图标优先 / 精确）没有持续指示

- 只在启动日志打一行「套装模式: 图标优先…」（`ui/run_tab.py:516-518`）。
- 报告/日志里看不出这一轮用的是哪种；复核报告时容易误判 `set_src` 分布。
- **建议**：状态条上加一枚只读徽标「套装判定：图标优先 / 精确」；报告 meta 里也记一份。

#### U-08 组合穷举：动作与结果都在折叠之下

- 输入有 8 张卡，`开始穷举/导出 CSV` 在第 8 张结果卡里（`ui/plan_tab.py:410-425`），
  结果表在按钮下面。760 高首屏只能看到 6 张卡。
- 跑完以后想改一个条件，要滚回上面；想再看结果，又要滚下来。
- **建议**：结果区改成主视图（sticky 顶部工具条：开始/取消/导出 + 状态 + 方案摘要），
  输入收进左侧抽屉/折叠面板；方案摘要写一行：「5 件套 · 凝夜白霜 · 攻击 · 满级件 · 门槛 120/100」。

#### U-09 结果表的可读性

- 复合列头：`评分和/有效分`、`加成区 60+45+0`、`排序分E`、`共效 9.2%⚠`；没有图例。
  底部一段 9pt 说明里还有**未渲染的 Markdown `**`**（见 U-12）。
- 数字左对齐、比例不等宽；行高 2 行；`COST` 列恒为 12（契约 ΣCOST≤12），零信息。
- `评分和/有效分` 列宽 158，比真正的排序键 `排序分E`（88）更宽 —— 视觉权重与事实相反。
- **建议**：拆成「P1…Pn / 评分 / 有效分 / E / 伤害」独立列或分组表头；数字右对齐 + 等宽；
  删 COST 列（在状态行写一次「ΣCOST 12」）；`加成区` 改成 `属伤+专伤+通用` 的分段条或三个小列；
  行话加 `title`/legend；表格上方给一行"按 E 排序，评分只算副词条"的提示。

#### U-10 报告行密度与"公式墙"

- 一行 ≈150px：180px 宽截图 + 5 行词条明细；1000px 高只能看 4 行（证据：`04_report_1440.png`）。
- 词条明细把公式全展开：`共鸣效率=10.0→10.0/9.4×10×0.6=6.38 [前40.78%]`；
  160 行 = 800 行公式。无效词条也占一行（`生命百分比=8.6 无效(0)`）。
- **建议**：默认行高 56px（缩略图 40×64 + 名称/套装/得分/判定）；点行展开词条与截图：
  - 词条行：`共鸣效率 10.0` 右侧 `6.38`，公式与分位放 `title`（悬停）；
  - 无效词条折叠成「另有 1 条无效」；
  - 判定列做成色块（见 U-11），不靠纯文字色。

#### U-11 判定色不可读且有两套

- 报告行内判定 `#4caf50/#009688/#2196f3/#ff9800/#f44336` 对白底：**2.78 / 3.67 / 3.12 / 2.16 / 3.68 : 1**，
  全部低于 4.5（正文 14px）。摘要 chips 用深一档的 Material 800，5.13~6.61（"建议强化" 3.79 仍不达标）。
- 同一判定两处两种颜色；「达标」和「保留」都是绿系，「不合格」与「不建议强化」都是红系 —— 语义层次不清。

## 5. 工作流适用性

**① 日常评估（目标 ~12 分钟）**
启动 → 等待 → 保存 → 浏览器里筛选。断点：

**② 强化**
设置套装/策略 → 开始 → 看日志。断点：
- 套装下拉里 37 个名字没有搜索；「通用」与具体套装的差别只在说明里。
- 传统模式的 9 个选项挤成一行（940 下会溢出）——CLAUDE 里也记为"仍是紧凑控件"。

**③ 组合穷举**

## 7. 设计方向（提案，不实施）

### 7.1 概念：调律台（Tuning Bench）

> 一句话：**像一台安静的仪器 —— 数据发声，装饰沉默。**

受众是同一个玩家，长时间对着它；屏幕上是 1 万条数据里的 160 件声骸。它的工作不是"展示功能"，
而是"让你在 12 分钟里知道发生了什么，并在 5 分钟里做完取舍"。所以：

1. **一个记忆点**：运行状态条（唯一允许有"仪表感"的地方）。
2. **数字优先**：所有数值等宽、右对齐、带单位；表格行高统一。
3. **语义色只给判定**，其余一律墨色/灰阶；装饰色只保留黄铜一条线。
4. **一层表面**：去掉逐卡阴影与圆角差异，用留白 + 1px 分隔线分组。
5. **文案即导航**：按钮说结果（"开始评估"），状态说事实（"第 3/8 屏 · 72/160"）。
